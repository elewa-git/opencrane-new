# Chat

This folder handles conversations between people and with assistants. It saves messages, sends assistant work to the right computer and returns replies and live updates while checking who may read each chat.

## What it is responsible for

- Creates direct, group and assistant conversations, and manages participants.
- Returns visible history, conversation lists and each person's archive and read choices.
- Starts assistant turns, delivers files and work, and checks reports before saving replies.
- Handles a person stopping a reply, spending stops and tool approvals.
- Keeps private sessions separate when people share an assistant's computer.
- Prepares side conversations and lets members review text before sharing it back to the parent chat.
- Refuses new work in closed chats and repairs unfinished work without disrupting other chats.

**Messages and access.** Two members can exchange private messages without starting assistant work. Members can start group chats with reviewed people. Offered groups are limited to those they belong to. Creators can add or remove participants; others can leave. Changes reject stale choices, and saved retries cannot add someone again. New chats can report that permissions are still applying so the website keeps the draft. A saved removal stops reads and live connections before the permissions service catches up. Later joiners see only messages from their latest join onwards. Lists reuse permission facts within a request and check for changes after each answer from the permissions service.

History loads before the final current-access check and before private text is opened. A removal during loading refuses the reply. Reads check access at that moment; they do not use the short write check. Commands load history first, then watch only the small records deciding access. A busy conversation cannot itself refuse a reader. Saved close checks remember the last position and read only new changes.

**Lists and personal choices.** The conversation list uses visible activity, visible titles for search and continuations naming only visible chats. Reaching its fixed scan limit returns an incomplete result rather than extra pages that could reveal hidden chats. Late joiners see their join time, including in personal sessions. Group lists show current participants without earlier creation details. The website loads the first page; paging controls remain planned. Archiving and read markers affect only that person and appear on other devices after the read tables catch up. Leaving and rejoining starts fresh choices. A lost reply can be checked by its original request id; checking starts no assistant work or spending.

**Assistant replies.** A turn is one message and the assistant's reply. The [bridge](../../../../GLOSSARY.md#bridge), the computer's connection to the server, receives work and returns progress. Waiting work is retried through short service outages until accepted, including after reconnecting. Finished chats are left alone while another reply is pending. Computer history is reused while unchanged and checked again before sending work or files, so new control intent holds waiting delivery. Each file is sent once per connection; its receipt, meaning confirmation of arrival, must come before that chat's turn. Waiting files leave spending stops and approval checks available. A slow chat read delays that chat rather than every chat. Shutdown waits for unfinished checks.

The server combines adjacent pieces of the same reply before saving them. It checks each piece against saved text before confirming it to the computer. Repeats are recognised without another save, including after reconnection. Accepted reports keep saving after the connection drops. Chat and computer summaries read new changes after their first load and save only if the stored position still matches the history checked. Each summary has a memory budget: a large one is dropped on its own, leaving others available. Saved failure reasons distinguish a person's stop request from a computer restart, model error or tool refusal. Message and stop requests refuse ids already used by another saved record, including a report.

**Live updates.** Open chat pages keep checking access when installation or group membership changes. Removing someone from a group closes their private session with its assistant within two seconds. If another permission update takes too long, the page reconnects after five seconds and resumes from saved messages. The server checks each open chat's feed position every 100 ms and loads content only when it changes. Computer status comes from a small read-table record updated by background workers. A sleeping or waking computer shows Starting; recovery lasts until a new ready record appears.

**Private and shared work.** Each assistant has one [computer](../../../../GLOSSARY.md#computer); a group shares its assistant's computer. Each member gets a separate private session and a [private turn](../../../../GLOSSARY.md#private-turn) by default. That turn gets earlier completed replies from the same member and starts a fresh [Codex](../../../../GLOSSARY.md#codex), the AI agent, without local tools. Live disk isolation remains unproven, so private-turn memory stays off. A [memory-free turn](../../../../GLOSSARY.md#memory-free-turn) can use the shared disk and browser but receives no earlier private context. Losing spending access does not remove the right to read or stop existing work.

Personal memory-free turns can receive a short list of reviewed, free tools available to both the person and assistant. Ask tools also need reviewed approval details. The gateway checks rights again for each call. The computer and gateway keep the reviewed Allow mode, so changing a tool to Ask refuses an old automatic call. The server checks whether a computer supports approval messages first; older computers get Allow tools only. Private turns with a group assistant stay restricted and receive no tools. [Memory](../memory/README.md) explains fact references and the extra checks before renewing a pass. Invalid older memory records do not prevent ordinary messages or stop requests.

**A person stops a reply.** The server gives a stop request priority over progress waiting to be saved. It uses the same saved chat summary as reports, rather than reloading every piece of a long reply. A separate check sends saved stop requests without waiting for normal turn or file delivery. A stop request records intent; the computer's later result says how the turn ended.

**A budget stops work.** Personal turns use the latest default paying group when queued; a paying group is the group charged for the work. A small shared summary reads each new spending change and provider switch-on change once. A queued turn keeps its saved payer and position. An applicable spending stop refuses it even after the limit rises or the default payer changes. Checks run again after saving the computer's start and before issuing a pass. Repeating a start checks current membership, while pass renewal and turn closure keep the original model and provider. A stopped turn cannot renew its pass.

The server saves a budget refusal before telling the computer that work cannot start. Reconnection recovers the spending notice even if the computer restarted before the notice was saved. Access is checked before returning a refusal, so a removed member cannot learn the payer's spending state. Saved spending stops go before files, turns and approval replies. The server checks after waiting for a connection or preparing work, then immediately before sending a turn. Unfinished stops repeat after a lost send or reconnect. A pending check holds only that chat; file receipts do not restart the check. Other turns on the computer can continue, and raising a limit cannot revive stopped work. These checks do not change chat reading or desktop viewing rights.

Authorised readers receive live notices for spending stops on requests they can see. The notice contains no amounts. Saved status survives reconnect and shows the reason and work state. Only the requester sees limits and call amounts, distinguishing money held, charged or released and calls that might have been sent. Reads start no work and still check access after a failed load. If a live update takes more than ten seconds to load, the connection closes so the website can reconnect and read saved status.

**Approvals and tool reports.** Tool starts and finishes are saved and appear in the feed. Approval cards name their turn so the website can hide choices after work stops. Replies preserve saved dates and cancellation reasons. A saved takeover cancels unused approvals for the same computer generation and turn. The bridge sends its local work gate before an approval reply, including after reconnect. An approval belonging to another person or installation gets the same refusal as a missing one. Changed tool rules or a failed tool-list check end a pending approval, even if a later check succeeds first. Approval reads run separately so one slow chat does not block others. Failed reads are spaced out, and the computer is told when another wait cannot be accepted. Missing details can be fetched; requester retries require proof that the call was not sent.

**Side conversations.** A child chat is a side conversation started from another chat. A member can review their own group message, select people and an assistant, then save the request. Separate commands create the child and wait for permissions before copying only the reviewed source message under the child's own encryption key. Repeats return the same saved records. The recovery worker reads unfinished requests from a table, checks the saved request and current access, and repairs missing creation or first input after restart. Proven refusals are saved; temporary access outages remain queued. Only the requester can read status. These newly requested children stay queued and cannot start assistant work yet; failed requests cannot be retried yet.

The context builder for an existing usable shared child includes completed exchanges from that child, including replies to other people. It excludes parent history, private sessions, files and unfinished text; the first turn uses only the saved reviewed source. Child output must match the computer, assistant, conversation, turn, requester and thread admitted by the server. A thread is the agent's separate working session for that chat. Later replies are checked against the access mode saved when work began. Only the start report states that mode. The creator can invite someone only after acknowledging that shared history becomes visible, remove others, or let others leave. Inviting someone grants access only to the child. People can recover their own saved leave result without reopening it. A link to the parent appears only while the reader may still read the source message; otherwise it returns no parent details.

Members can review a completed child answer, a saved reply from a running turn or their own interim update before sharing text to the parent. The entry credits the publisher. Files are unavailable. Failure or lost output before saving the parent entry invalidates the review; unrelated child messages do not. Sharing text here is separate from publishing tool-server settings in [integrations](../integrations/README.md).

**Closed chats.** Saved closure refuses new passes and rebuilt context. Displayed assistant output stays as it was at closure: later reports, decisions, tool sends, child publications and agent or system posts remain saved but hidden. Human posts remain visible, and the list keeps showing Closed. Waiting inputs receive saved failures; admitted work receives a stop request while its original computer is ready. Cleanup survives restarts and older close records, repairs missing computer-turn endings and never wakes a suspended computer or resends input. A delayed shared start after cleanup is refused, but its matching failure report can finish saving. Output still needs an admitted start. Acknowledging delayed reports keeps other chats on the same connection working. Public closing requests are not available yet.

The server renews computer passes through authenticated Kubernetes management access as root. It sends the signing public key so the computer can verify the pass and save its identity. Desktop and Codex processes cannot replace passes through HTTP. [Computers](../computers/README.md) explains control intent, which blocks new work without granting control.

## How it connects

The [server](../../README.md) registers chat requests and live connections for the [website](../../../web/README.md). [Members](../members/README.md) checks membership; [assistants](../assistants/README.md) defines shared assistants. [Files](../files/README.md), [computers](../computers/README.md), [memory](../memory/README.md) and [providers](../providers/README.md) supply attachments, desktop access, remembered facts and model choices. [The assistant computer](../../../computer/README.md) runs the work. [Shared models code](../../../../libs/models/README.md) decides spending and tool access; [background workers](../../../ops/README.md) keep read tables and permissions current.
