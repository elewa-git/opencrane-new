## Why and functional outcome

An operator needs a disposable ERP against which later MCP work can prove real
user rights and attribution. [infra/odoo](../../infra/odoo/README.md) provides
start/reset/stop, synthetic drafts, two ordinary users and direct JSON-2 checks.
The restricted order and its lines have a global Odoo record rule; the reader
has a read-only ACL and the writer has native own-sales rights.

## Architecture and custody

The fixture has a fixed Compose project, separate database and filestore volumes,
and two internal networks. PostgreSQL is unpublished; Odoo has no published
container port or runtime internet route. A Debian socat relay binds only
`127.0.0.1:18069` and forwards to `172.30.52.2:8069`. Docker 29 suppressed the
original port publication on internal networks, so the relay preserves isolation.
The operator-owned `opencrane-odoo-mcp-upstream` network is reserved for the named
future workload; [policy](../../infra/odoo/upstream-policy.json) fixes identity,
address, port and refusal of arbitrary remote registration. Docker operators
remain trusted; workload admission belongs to P3-12.

Keys are generated by Odoo in secure setup, expire after 12 hours, and exist only
as mode-600 files below `~/.config/opencrane/odoo/` (mode-700 directory). Keys,
passwords and bearer values never appear in argv, source, events or output.
The checks read files directly and disable HTTP proxies. No administrator
credential is used for the authenticated checks. Local shell administration is
used only to initialise fixtures, ACLs, rules and ordinary-user keys.

The full pinned Community source remains available: removing uninstalled module
metadata broke base catalogue setup, so no patched installer is maintained.
Only the 54 Community modules selected by `sale` are installed. Seeded ERP data
belongs to this external test system; no OpenCrane business state or event type
changes, SQL business rules, shared-stack changes or restarts are introduced.
